Puedes encontrar problemas en este modo de guardar backups? y comprarlo con el estandar o si hay mejores opciones?

Tu caso: cada X tiempo generas un ZIP en texto claro con los datos del usuario y quieres guardarlo cifrado con una contraseña que el user sabe hoy, pero que siga siendo recuperable en 1 mes aunque la contraseña cambie, subas el costo del KDF, etc.

La solución práctica es:

Idea clave (sin humo)

Cifrado por sobres (envelope encryption) + “key slots”.

DEK (Data Encryption Key): clave aleatoria por backup que cifra el ZIP.

KEK (Key Encryption Key): se deriva de la contraseña del usuario (Argon2id) o viene de un passkey/hardware.

Guardas la DEK envuelta (“wrapped”) con uno o varios KEK en un encabezado del backup.

El ZIP siempre se cifra con la DEK (nunca directamente con la contraseña).

Así, puedes cambiar la contraseña sin re-cifrar el ZIP: sólo vuelves a “envolver” la DEK y listo.

Piensa en el backup como:

[HEADER: { key_slots: [ ... ], suite, versión, salt, kdf_params, ... }]
[DATA: ZIP cifrado con AEAD usando la DEK]

¿Qué pasa en 1 mes? (casos reales)

El usuario recuerda la misma contraseña

El lector del backup lee el HEADER, ve un key_slot de tipo “password”.

Deriva KEK = Argon2id(contraseña, salt guardada en el header).

Desenvuelve la DEK, y con esa descifra el ZIP. Fin.

El usuario cambió su contraseña hace 2 semanas
Opciones sanas:

Key slots múltiples: cuando el usuario cambie la contraseña, tu app añade otro key_slot para ese backup (o en un sidecar .keys), envolviendo la misma DEK con la nueva contraseña.
→ En 1 mes, cualquiera de las dos contraseñas sirve (ideal para transición).

“Backup Passphrase” estable: defines (opcional) una contraseña de respaldo que no cambia con la contraseña diaria. Siempre existe un key_slot para esa passphrase.
→ En 1 mes usas esa passphrase si la principal cambió.

El usuario olvidó la contraseña

Ten otro key_slot con passkey/hardware (TPM/Keychain) o con una “recovery key” (código de 20–24 palabras) guardada fuera de banda.

Con cualquiera de esos key slots, desenvuelves la DEK y listo.

Subiste el costo de Argon2id (o cambiaste el algoritmo)

El header del backup viejo ya guarda los parámetros (salt, m/t/p).

En 1 mes, descifras usando los parámetros del header sin drama.

Cuando tengas tiempo/clave, puedes re-envolver la DEK con parámetros nuevos (más costosos) sin tocar el ZIP cifrado.

Lo mínimo que debes guardar en el HEADER

Formato simplificado (puede ser CBOR/JSON binario, me da igual mientras sea estable y autenticado):

{
  "magic": "KPB1",
  "version": 1,
  "suite": "xchacha20-poly1305",   // o aes-256-gcm-siv
  "created": 1736467200,           // timestamp
  "file_id": "16 bytes rand",
  "key_slots": [
    {
      "type": "password",
      "id": "slot-01",
      "kdf": { "alg": "argon2id", "salt": "16b", "m": 256, "t": 3, "p": 1 },
      "wrap_alg": "aead",          // envuelve la DEK con AEAD
      "wrap_nonce": "24b",
      "wrapped_dek": "ciphertext"
    },
    {
      "type": "passkey",           // opcional
      "id": "slot-02",
      "wrap_alg": "aead|hpke",
      "wrapped_dek": "ciphertext"
    }
  ],
  "min_suite": "KP-1"              // anti-downgrade (opcional)
}


Y todo el HEADER se autentica (lo usas como AAD del AEAD) para impedir cambios silenciosos.

Tu flujo en 3 pasos
Al crear el backup (hoy)

Haces el ZIP en claro.

Generas DEK aleatoria (32 bytes).

Derivas KEK de la contraseña con Argon2id (guarda salt y parámetros).

Envuelves la DEK con ese KEK → produces un key_slot.

(Opcional) Añade otro key_slot con passkey/hardware o “backup passphrase”.

Cifras el ZIP con AEAD (XChaCha20-Poly1305 o AES-GCM-SIV) usando la DEK.

Escribes HEADER + DATA, y borras el ZIP en claro.

Al restaurar (en 1 mes)

Lees el HEADER → eliges un key_slot compatible (password/passkey).

Derivas KEK según el slot → desenvuelves la DEK.

Descifras el ZIP con esa DEK. Hecho.

Si el user cambia la contraseña mañana

Tu app, si ve el backup accesible (o su .keys sidecar), hace:

Desenvuelve la DEK con la contraseña vieja (que aún conoce hoy).

Crea nuevo key_slot con la contraseña nueva.

No re-cifras el ZIP. Sólo añades/actualizas el HEADER (o el sidecar backup.zip.kpbkeys ligado por file_id).

Truco sidecar: si no quieres tocar el archivo de backup (inmutable), guarda los key slots nuevos en backup.zip.kpbkeys. Al restaurar, tu lector busca key_slots primero en el sidecar y, si falla, en el header original.

Reglas prácticas (para que no se rompa nada)

AEAD: por defecto XChaCha20-Poly1305; alternativa AES-256-GCM-SIV.

KDF: Argon2id con autotune (≥256 MB y ≥200 ms en desktop; menos en móvil si hace falta).

Múltiples key slots: siempre al menos 2 (contraseña actual + passkey/backup passphrase).

Versiona suite y version en el header.

Autentica el header completo (AAD) para evitar downgrades.

Borra el ZIP en claro tras cifrar; y opcionalmente firmar el backup (firma Ed25519) si quieres detectar corrupción fuera del AEAD.

Qué decirle al usuario (mensaje humano)

“Este backup se puede abrir mientras recuerdes cualquiera de: tu contraseña de ese momento, tu backup passphrase, o tu passkey del dispositivo.”

“Si cambias tu contraseña, tus backups siguen funcionando; nosotros actualizamos los permisos (key slots) sin re-cifrar los datos.”

Corto y al grano:

1) ¿Se rota la DEK?

Para backups periódicos (tu ZIP cada X tiempo): sí, pero “al escribir”. Usa DEK nueva en cada backup. Eso ya es rotación natural y no te cuesta nada extra.

Para un backup ya escrito: rotar la DEK implica re-cifrar todo el archivo. No hay “rotación sólo de header”. Si no hay motivo fuerte, no lo hagas: rota sólo la KEK (la derivada de la contraseña) re-envolviendo la DEK.

2) ¿Cuándo rotar DEK “de verdad”?

✅ Compromiso o sospecha de fuga de la DEK.

✅ Cambio de algoritmo/suite (p.ej., pasar a AES-GCM-SIV o XChaCha) o parámetros de seguridad que afectan al dato.

✅ Políticas que exijan “re-clave” completa (compliance).

❌ Cambio normal de contraseña: basta re-envolver la DEK con la nueva KEK (no re-cifras datos).

Procedimiento seguro para rotar la DEK de un backup existente

(implica re-cifrar; hazlo sólo si toca)

Abrir backup viejo → leer header → desenvolver DEK_old (con algún key slot válido).

Generar DEK_new aleatoria.

Crear header nuevo: mismo metadata, nuevos key slots (con la(s) contraseña(s)/passkeys actuales), DEK_new envuelta.

Stream: leer en chunks → descifrar con DEK_old → cifrar con DEK_new → escribir a archivo temporal (.tmp).

Trailer/verificación: escribir trailer autenticado; verificar bytes/etiquetas.

Swap atómico: rename(temp → backup_nuevo) y marca el viejo para borrado seguro.

Opcional sidecar: si usas .keys, actualízalo con los nuevos key slots.

Esto es “rekey” completo. Es la única forma real de “rotar DEK” sin dejar utilizable la DEK vieja que ya pudo haberse filtrado.

“Rotación barata”: re-envolver DEK (rotar KEK)

Para cambios de contraseña o añadir métodos de recuperación:

Añade key slots nuevos (contraseña nueva, passkey, recovery key) que re-envuelven la misma DEK.

No tocas el ZIP cifrado → rápido y seguro para el caso normal.

Ojo: si la KEK vieja se filtró y un atacante ya desenvolvió la DEK, re-envolver no sirve; ahí sí necesitas rotar DEK (re-cifrar).

Reglas simples para tu diseño

Cada backup nuevo ⇒ DEK nueva.

Header con múltiples key slots (contraseña actual + passkey/backup passphrase).

Cambio de contraseña ⇒ re-envolver (no re-cifrar).

Incidente/algoritmo roto ⇒ rekey total (rotar DEK + posiblemente suite).

Retención: mantén N generaciones; al expirar, destruye la DEK (y el archivo) de las viejas.
